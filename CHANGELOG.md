# Changelog

## Unreleased — Console, vehicle config and Service Mode

- **The EU market switch waits for Apply.** It is part of the Vehicle tab's Apply (one save, one restart) and no longer snaps back before you press it. Applying a changed market also moves the simulated location to the first city of the new market (Paris or New York), so the car does not loop between regions.
- **Jump to a city.** Controls > Navigation has a **Jump to** selector that follows the market switch: with EU market on it lists Paris, Berlin, Munich, Frankfurt, London, Amsterdam, Rome, Madrid and Barcelona; otherwise New York, Los Angeles, San Francisco, Seattle, Austin, Chicago and Miami. It fills Latitude and Longitude, which move the simulated GPS as before; it does not switch the market, and navigation needs a map image that covers the city.
- **The panel is more responsive on the Debug, CAN, Gateway and Controls pages.** Frequent, short backend actions (status, previews, debug, CAN, controls and the service setters) now reuse a warm `backend.py serve` process instead of starting a new interpreter for every call, which cut about 75 ms from each one. Long actions (import, setup, start, stop) still run as one-shot processes.
- **Controls panel pages scroll clear of the bottom bar (Model 3 single display).** The panel is bottom-aligned on the 1200 px screen, so its tab list and settings pages scrolled 100 px under the bar and their last rows (such as Navigation › Third-party Charging Stations) could not be reached. Window padding and margin do not move the panel, so the layout layer now leaves 100 px at the bottom of the tab list (`TabLayout`), the settings pages (`PageLayout`) and `ScrollableSettingsPanel`. Checked on a running session for the tab list and the Navigation page; restart the session to pick it up.
- **Debug log sources show an approximate line count.** The source dropdown lists each log as, for example, `keep-awake (100+)`, using coarse buckets (1+, 10+, 100+, 500+, 1000+, then steps of 500) so refreshes stay cheap.
- **The Vehicle selector no longer says "Model 3/Y … only the Model S/X interface" on a Model 3 image.** The backend judged the layout from the last started session's `config.json`, so a stale or missing one made it refuse Model 3/Y. The GUI now sends the selected device's layout with every `config-values` request.
- **Controls categories are a side list.** The services panel (Drive, Wheel buttons, Vehicle, Climate … Alerts) was one overflowing tab row; it is now a category list beside the page.
- **Vehicle selector.** The Controls services panel has a new first tab, **Vehicle**: Model 3 or Model Y, paint, wheels and Autopilot hardware (`VAPI_driverAssist`: HW1 to HW4), plus the EU market switch moved from Navigation. Apply saves the car-config overrides and restarts the device after confirmation. `GTW_dasHw` is not touched. Names come from the 2026.26.6.1 image's `libSharedProto` enums; the paint and wheel readbacks on a running session are not yet validated.
- **Changing the location warns when no map is loaded.** Editing latitude or longitude in Services › Navigation with **No map image** selected now shows a notice that navigation may not work there.
- **Experimental Model Y profile.** On the Model 3 single-display (ICE/MRB) image, setting the Vehicle config value `VAPI_carType=ModelY` now selects a Model Y profile (chassis `Y`, restraints `NAMY`, wheel `Crossflow19`) instead of failing at start with "The vehicle profile does not match this firmware layout." Model Y is refused on the S/X layout like Model 3. Labels come from the 2026.26.6.1 vehicle library and are not yet validated on a running session.
- **The Model 3 HVAC panel is lifted by the same 100 px.** The layer also moves the HVAC panel's fixed `Y` offsets up, so its vent, fan and recirculation row is no longer hidden behind the bottom bar. The Climate Keeper bar (Off / Keep / Pet / Camp) moves with it.
- **The Model 3 Controls panel starts under the status bar.** The firmware draws the panel 1040 px tall, bottom-aligned on the 1200 px screen, which left a strip above it and hid its last 100 px behind the bottom bar. Single-display sessions now mount a lab layer (`layout/`, generated per session, below your own replacements and above the read-only image) whose `styles-M3.conf` sets `ControlPanelHeight` to 1140. The layer is skipped when the image's file differs from the expected line. Other windows that use `ControlPanelHeight` follow the new value; only the Controls panel has been checked.
- **Single-display (Model 3 ICE) sessions run about 2.5× faster.** Their Xephyr screen no longer uses glamor: QtCar paints in software there, and glamor's upload path held the center display to about 4 fps at 150% display scale (about 10.6 fps now, and the 3D car view rose from about 37 to 53 fps). Dual-display MCU2 sessions keep glamor. Restart the session to pick it up. The map's tile loader no longer stays offline after a start: connectivity is written only after the first internet probe, not from the "offline" default. A saved config row whose value contains a NUL character is now refused instead of failing on every start, and `media-apparmor.profile` no longer defines `QtCarTMServer` twice; rerun Runtime Setup so `QtCarGpsManager` gets its peer profile.

- **Merged with upstream `06066060606060/tsla-infotainment-lab`.** Both histories are kept. **CAN & gateway** is now two tabs: **OS traffic** (observation and frame injection) and **Lab gateway** (the emulated gateway with bus profiles, unlock and frame send). **Diagnostics** keeps its Alerts, Logs, Environment and Console tabs and gains **Firmware files** (firmware replacements); **Debug** is its own page after Vehicle config. Offline navigation uses the owned Valhalla and TM server from `navigation.py`; the GPS manager and lab GPS feed run on top of it. The Service Mode panel uses the image's `opt/diag` backend when present, with the alert and VehicleService stand-ins.

- **The firmware's HVAC and VAPI pushes no longer fail.** The firmware sent them to `com.tesla.VehicleService`, which nothing in the lab provided, so each push logged `Proxy does not exist for com.tesla.VehicleService`. A stand-in (`runtime/vehicle-service.py`) now owns that name and passes reads and writes to the center display, as `com.tesla.Debug` does. It starts with the session; restart the session to pick it up.
- **Diagnostics has Alerts, Environment, Console and Firmware files tabs.** The Console moved from its own sidebar entry into Diagnostics, and its **Connect** button carries a terminal (SSH-style prompt) icon. Its Logs tab is gone: **Debug logs** (below) shows every session log. **Environment** holds Check environment and its results and replaces nothing else. The one-shot local logs dump is gone. Vehicle configuration is now the last sidebar page.
- **The Service Mode gateway lock follows the lab unlock.** The firmware's Service Mode "Confirm User Presence" dialog stayed on `GTW LOCKED` no matter what the CAN panel showed, because nothing drove the gateway signals it reads. The CAN service now records its unlock state (and expiry) in `session/gateway-lock.json`, and keep-awake projects it onto `GTW_diagLevel` (`LEVEL_SERVICE` while unlocked, else `LEVEL_NORMAL_OPERATION`) and `GTW_diagRemainingSeconds` on `QtCarDvServer` and the displays — the signals from which the page computes its own unlocked state. Pressing **Unlock gateway** in the CAN panel now turns the dialog to Unlocked with a live countdown. The lab unlock is its own HMAC handshake, not a vendor key check and no signed token; the lab cannot satisfy the real key/brake/turn-signal presence conditions, so the panel's unlock is the authority. Restart the CAN service after updating.
- **Service Mode and the CAN gateway work together.** Entering Service Mode on the display, or with the Modes switch, now reaches the CAN service: it follows the displays' own state as well as the desktop's, so changes made on the touchscreen show up on the bus. A new periodic `LAB_vehicleModes` frame (`0x5E1` on `veh`) carries Service, Developer, Factory, Transport, Showroom and Dyno mode. The gateway's diagnostic route (`0x641` to `party`) now passes only while the gateway is unlocked **and** Service Mode is on; its status and the CAN panel show Service Mode. A task run from the Service Mode panel is offered to the gateway as a `LAB_gatewayRequest`, and its error names what the gateway decided: not running, locked, Service Mode off, or passed with no ECU to answer. Tasks still never run. Restart the CAN service after updating.
- **Vehicle alerts in Service Mode.** Services › Alerts raises and clears alerts by name (for example `VCFRONT_a097`). A stand-in for the vehicle's alert daemon (`runtime/alertd.py`) serves them on `com.tesla.Alerts`, where the firmware's Service Mode backend reads active and recent alerts; the panel lists them on the matching sections. It replaces the image's own `alertd`, which only learns alerts from vehicle CAN and so never had any. The center display's QtCar polls the same service; whether it shows them is not yet verified. Nothing is sent to a vehicle.
- **Full CAN bus from public Tesla databases.** The CAN service takes a bus profile: `model3` (opendbc's Model 3 vehicle and party buses) or `models` (Model S/X CH, PT, BDY, BFT, OBD and the gateway's ETH bus, from tesla_can_signals and opendbc). The databases are downloaded at a pinned commit into the data directory on first start and are not part of the repository. Every periodic frame is transmitted with rolling counters and Tesla checksums, and multiplexed frames step through their pages. Gear, speed, pedals, steering, stalk, lamps, door latches and temperatures follow the session. Accepted or injected frames change the session the same way the `LAB_*` frames do, and the gateway routes are generated from the loaded table. The `.dbc` reader now handles value names, multiplexing and cycle times, and `load-dbc` also reads tesla_can_signals JSON. For SocketCAN with the `models` profile, run `can-setup` again (it now creates `vcan0`–`vcan5`).
- Fixed **Unlock gateway** doing nothing in the CAN panel. The GUI dropped a CAN request while another one (such as a refresh) was still running, so the unlock challenge could be lost without a message. CAN requests now run side by side, the unlock is a single request that runs the handshake in the backend, and the status line updates at once, showing the time left. In QEMU mode, the chosen CAN transport now reaches the guest.
- Fixed the CAN gateway letting an extended (29-bit) frame through a standard-identifier allowlist when its low 11 bits matched, for example `0x100003F5` passing as `0x3F5` while unlocked. Extended frames are also no longer decoded as, or applied as, the standard lab frame with the same low bits. Restart the CAN service after updating.
- Fixed the CAN trace failing as a whole once a loaded `.dbc` defined an extended frame and one was on the bus. The `.dbc` reader now also honours the extended flag (bit 31) on identifiers below `0x800`.
- **Alerts & DTCs in Service Mode.** keep-awake now keeps `FEATURE_enableSUIAlertsPanel` on in `QtCarDvServer`, which opens the Service Mode panel's Alerts & DTCs tool listing the raised alerts. It was lost whenever the session restarted, for example on entering Service or Transport Mode.
- Fixed Services › Alerts refusing most real alert names: a name's suffix may now contain underscores (`BMS_w001_HW_Over_Current`, `BMS_d001_Internal_Batt_Failure`). A name the image does not define (compiled into its `libQtCarAlerts`) is now refused, since QtCar lists it as a blank row; `VCFRONT_a097`, the old example, is one of those on 2026.8.3 MCU2 images. Clearing accepts any name.
- Fixed the CAN gateway service stopping when the panel closed. It is now started in its own session, so it lives until stopped, as documented.
- Fixed Exit Service Mode failing in the Service Mode panel (`com.tesla.Debug was not provided`). Only `QtCarServer`, which the lab does not run, serves that name; the Odin stand-in now provides `com.tesla.Debug /Debug`. `set_data_value` (with its if/unless guards) and `get_data_value` go to the center display, so a write reaches the lab's state like a touch there; `get_data_values` lists `QtCarDvServer`'s store as text or JSON.
- Fixed the Service Mode updater view failing with a 500 (`/var/log/udsdebug.log` missing): the backend sees an empty log in its namespace.
- keep-awake no longer writes `LINK_wifiOnlineCheckFailure`, which neither display defines.
- Fixed driving controls reaching the displays 1–2 s late. keep-awake read all ~200 watched display-request names from the center display every 0.5 s, and QtCar answers each read on its GUI thread, so a 50 ms control tick took 1–2 s. It now reads 16 of them per 0.25 s tick (a full pass takes about 3.5 s), which keeps the center display near 220 reads/s instead of the ~300/s where QtCar saturates, and display-link no longer re-introspects both displays four times a second.
- Fixed Service Mode Vehicle Info showing no Firmware and a `--` odometer. The panel's backend reads `QtCarDvServer`'s own data-value store, which the lab never wrote; keep-awake now mirrors `VAPI_carVersionString` and `VAPI_odometer` there. It also writes the profile's `VAPI_carType` there, so the panel's chassis type matches the displays; that is a car-config value, so it is written once per `QtCarDvServer` start and only when the stored value differs, and a change restarts SpotifyServer and ChromiumAdapter once. `GTW_dasHw` (Autopilot Hardware) and `MCU_transportModeOn`/`MCU_showroomModeOn` are not defined by QtCar or `QtCarDvServer` in 2026.8.3 and are reported `unsupported`.
- Fixed the Service Mode backend's CAN-over-Ethernet task panicking at start (`Failed to bind socket … AddrNotAvailable`): it binds `192.168.90.255`, which its private network namespace now owns too. The backend's main thread still busy-loops once its Odin websocket connects (about 600,000 eventfd wake-ups a second, against any websocket server; the loop is inside the firmware binary), so the lab now runs it in a systemd scope capped at 25% of one core and bound to the session unit. Without a systemd user manager it runs uncapped and the supervisor log says so.
- **Why Spotify cannot log in.** Spotify's QR-code login (and Apple Music, Apple Podcasts, TuneIn refresh) goes through a Tesla vehicle service, which the lab blocks, so its page shows "Connection failed". Amazon Music and Audible sign in with their provider directly. The Media status line and `docs/media-runtime.md` now say so instead of suggesting a Spotify login check.
- Fixed the Showroom and Dyno test mode switches doing nothing. They wrote names QtCar does not define (`ESP_messageDynoModeActive`) or does not display from alone; Showroom now also writes `GUI_showroomMode` and Dyno writes `VAPI_dynoMode`, both found in the 2026.8.3 image's QtCar strings.
- **Service Mode Vehicle Info shows Firmware and Autopilot Hardware.** The firmware's `service-ui` backend builds these from data values: `VAPI_carVersionString` and `GTW_dasHw`. Each display start now writes the image's own version as `VAPI_carVersionString` (from `/etc/customer-version` and the build id in `/etc/build-info`, e.g. `2026.8.3 (develop-…)`), and `GTW_dasHw` comes from an imported config or a value added under Vehicle config: `MONOCAM` (1.0), `PARKER_PASCAL` (2.0), `PARKER_PASCAL_2_5` (2.5) or `TESLA_AP3`. VIN stays empty.
- **Transport, Showroom and Dyno test mode switches.** Services › Modes now has switches for Transport mode (`GUI_transportMode`, `MCU_transportModeOn`), Showroom mode (`MCU_showroomModeOn`) and Dyno test mode (`ESP_messageDynoModeActive`), off by default. The names come from the firmware's service-ui data-value list and are not yet observed on a running display, so check each switch's firmware response. Nothing is sent to vehicle hardware.
- **Odometer.** An Odometer (km) control on the Energy tab writes `VAPI_odometer` in miles, which the Service Mode panel's Vehicle Info shows as "mi / km" instead of `--`. It defaults to 10,000 km.
- Fixed the Service Mode panel looking cramped at Windows scales above 100%. Its browser zoom was fixed at 1.25 while the card grew with the display scale, so the page got fewer CSS pixels and its labels wrapped. The zoom now shrinks by the display scale (0.833 at 150%), keeping the layout the panel has at 100%.
- Display setting requests also pair with other status names in the image that contain the setting's name (for example fog lights), and a flag pairs with On/Off lamp states. A refused request records the value the display kept, and an unrouted one lists related names, so a route can be written from the feedback file.
- **Display settings take effect.** Settings the center display requests without a lab control (such as an acceleration mode) no longer snap back: the lab finds the image's `GUI_*Request` values, and when one changes it writes the choice to the matching status values the display exposes, reads them back, and restores it after a display restart. `session/request-routes.json` can name the status values explicitly or disable a request. `display-requests-feedback.json` lists every request with its result and every D-Bus call the firmware made to a service or method the lab does not provide.

- Restored the native Start Self-Driving panel in explicitly configured Model 3 lab sessions. It is constructed before late profile writes and revealed after native view creation completes. Added an opt-in Self-Driving UI simulation under Controls: the blue Start button selects simulated ActiveFsd, and Stop returns to Available. Disabling restores the previous AP state; each restart begins disengaged. Simulated requests remain local and never change speed, gear or steering. With simulation off, native button availability remains authoritative.

- Recheck explicitly selected local FSD UI inputs with firmware readback every two seconds so late service defaults cannot silently replace them. Other settings retain change-only writes, and learned vehicle configuration fields are excluded. Enabled the existing session's Start FSD from Park preference; the native Start button remains unavailable without Autopilot feedback.

- Corrected the Model 3 navigation-country GUI field to the ISO alpha-3 value `USA`. Documented a local map-coverage override for the FSD menu exercise, removing the native regional message while preserving GPS coordinates and read-only firmware.

- Documented and validated a session-only Model 3 FSD menu setup using an AP3 hardware profile, local feature/preferences and an explicitly simulated FSD map-availability flag. Native readback survives restart; no driving engagement or FSD controller is supplied.

- Added an opt-in Park Assist simulation under Controls with ten adjustable ultrasonic distances in centimeters and a failure switch. Native status, service and sensor-interface health accompany the distances; disabling or failing the simulation clears stale obstacles. On the local Model 3 image, the USS preference restores the native distance arcs and removes the unavailable warning when healthy.
- Enabled the native Audio source selector by default in the Model 3 profile (`GUI_enableSourcePicker`). The Sources section and its individual visibility switches are now available without changing media accounts or subscription requirements.

- Replaced the browser landing page with a clearly identified local test page, adding a local HTTP check, viewport details and keyboard-event count alongside touch/drag, audio, generated video, scroll and WebGL checks. The tests no longer link to an external site; the source and staged runtime locations are documented.

- Fixed the Model 3 visualization refusing the rightward expansion gesture in Park. The single-display desktop adapter now permits the parked layout using native state queries, retaining the track-mode exclusion and normal behavior outside the opt-in.
- Fixed Service Mode remaining on its startup screen on newer ICE images. Detect the diagnostic web backend under `opt/diag` independently of the Odin task assets under `opt/odin`, and supply its missing boot-generated model selector through a session-only, read-only path adapter. Vehicle/gateway credentials and authentication remain unchanged.

- **FRAME INJECTION.** Replaced Lab gateway tools in CAN & gateway with continuous, individually enabled echo rules for observed native Gateway Ethernet frames. DBC signal overrides preserve all unselected bits from each new source frame, with explicit local destination, applied-state acknowledgement, echo/skip counters, disable/delete and Stop all. Rules start disabled, stop on device restart or DBC change, and do not capture their own sends. Invalid or ambiguous edits are refused; checksum recovery and physical CAN forwarding are not inferred.

- **OS traffic observation.** CAN & gateway now opens on a passive view of the running firmware's raw gateway records and decoded signals, with Party, Chassis, Body/VH and Gateway/Ethernet filters, display pause and CSV copying. Model 3 sessions start the native vehicle emitter with private output sockets and shared-memory IPC. Successful loopback UDP sends are distinguished from gateway API requests. The selected firmware supplies message names, units and enums; a user-selected DBC supplies bit layouts. Ambiguous multiplex definitions are omitted, and no physical CAN bus is inferred from Ethernet message numbers. The independent emulated LAB gateway remains available through the CLI.

- **Panel 0.5.5.** Model 3 sessions run the firmware's asset generator in an owned worker with a shared session cache, restoring the configured vehicle illustration in the tire card. The card no longer waits on a decorative asset-generation spinner. Media apps such as TuneIn use the firmware's toolbar controls to hide the browser address bar while preserving native window and D-Bus integration; normal browser navigation remains available.

- Fixed the native PARK telltale remaining in Drive by sending simulated parking-brake state with gear changes. Model 3 sessions now declare support for the native expandable visualization layout; the saved visualization preference controls its swipe gesture.

- Fixed simulated tire pressures staying local instead of appearing in the native Tesla interface. All four wheels now feed the Conti and Tesla TPMS display fields in bar, with native unit formatting and per-field readback.

- Removed the native "USING TESLAMAPS" debug banner by selecting the map engine through the session vehicle profile instead of the debug force override.

- **European maps and offline routing.** The library accepts EU and NA TeslaMaps SquashFS images, including `.ssq` files, with bounded multiline version metadata. Native sessions connect the selected read-only tiles and address database to owned Valhalla and TeslaMaps processes using private IPC and loopback TCP listeners. Simulated and replay GPS feed the native routing origin with a fresh estimate clock; coordinate readback and periodic verification restore lost fixes. Map status distinguishes the local routing engine from Internet-dependent street imagery. European route guidance was verified in the Model 3 ICE session.

- Fixed ICE startup crashing after the native Splash Screen Mode was saved. A narrowly matched display-state shim skips the early `restartTimer` callback while its active state is still null; initialized callbacks and other implementations pass through. The local splash-screen setting was disabled and saved as a configuration override.

- **Model 3 vehicle configuration.** ICE/MRB sessions now load a dedicated experimental Model 3 RWD profile instead of disabling vehicle-profile writes. The native UI, state writer and media server share that identity; the ICE target follows the image's launch environment and the version follows the selected image. Invalid numeric defaults were corrected using the 2026.26.6.5 ICE enum names (chassis ordinal 3 was Model Y), with previous local signals retained as reference metadata. Vehicle config defaults, saved edits and imports are separated by Model 3 versus S/X layout; numeric enum labels such as chassis `"3"` remain strings. S/X retains its original defaults. Profile writes report firmware readback, including rejected or mismatched values. Generic firmware compatibility remains experimental.

- Fixed firmware startup reporting a missing `usr/share/fonts` after a WSL restart even when fonts exist. The desktop worker and systemd service can see different mount namespaces; the supervisor now establishes its firmware, replacement view and map mounts inside the service before reading the image.

- **Firmware replacements.** Diagnostics can replace existing files in an imported SquashFS through a read-only overlay, with per-image persistence and restoration of individual originals. The original image is unchanged. Active sessions block edits; Stop releases overlay mounts before SquashFS mounts, and Full reset removes replacements. Native setup includes `fuse-overlayfs`; QEMU uses a private read-only replacement snapshot and requires an updated guest build.
- **Debug logs replace the Diagnostics Logs tab.** The Debug page is now **Debug logs** with a bug icon and the one place for logs; the duplicate Logs tab and its `session-log`/`logs` worker actions are removed. It refreshes every second, reads its journals side by side so a refresh is faster, and keeps a text selection while it refreshes.
- **Debug page.** A new page below Diagnostics shows bounded process logs and OS debug output, with automatic refresh while visible, source selection and a line filter. Native mode labels the host kernel and session journal. QEMU serial output remains available before guest journals can be read. Raw logs remain outside public diagnostic reports.

- Fixed the Service Mode panel reloading forever after a WSL restart. Runtime Setup now enables the AppArmor service and, on WSL, mounts securityfs at boot, so the lab's profiles are loaded again at every boot; without them `QtCarDvServer` rejects QtCar, the panel never learns that Service Mode is on and its watchdog keeps reloading it. A process that starts without its profile is now logged by name.
- **Display scaling on WSL.** The lab reads the Windows display scale and draws at that size instead of 100%. The panel scales through Qt. The center and instrument displays start the firmware at a larger window scale (`--window 0.9` instead of `0.6` at 150%) on a matching larger Xephyr screen or QEMU guest output, so text stays sharp and touches stay aligned; the size is reduced to fit the desktop. QEMU mode needs a rebuilt guest image. `INFOTAINMENT_LAB_SCALE` overrides the factor. The WSLg fractional-scaling setting suggested earlier blurred windows and enlarged the cursor; `python3 -m infotainment_lab.display_scale --disable-wslg-scaling` removes it.
- **Alerts instead of popups.** Refused or unknown configuration keys now raise an alert listed under Diagnostics › Alerts, with a warning icon and count on the Diagnostics sidebar entry, instead of a modal dialog. Adding a personal key by hand (for example `GUI_valetModePassword`) is refused right away with an alert naming the reason.
- **Alerts say why the firmware restarted.** Each car-config restart is recorded (`config-restarts.json`) and listed as an alert naming the display and the values it restarted for; Apply-and-restart and values reset after a restart loop are listed too, and the status banner names the values while the restart runs. The Alerts card stays in place with an empty state after Clear all, and alerts are plain rows that scroll with the page instead of a nested list.
- **Firmware cannot reach Tesla.** Names under `tesla.com`, `teslamotors.com`, `tesla.services` and `tesla.cn` no longer resolve for any firmware process or browser the lab starts. A preloaded shim (`native-netguard`) makes those lookups fail in QtCar, the cluster, Spotify, the media adapter, the data-value server, the visualization and `media-webapp-server`, and each log records `netguard: blocked lookup of …`. Chromium refuses the same domains through its resolver rules. The local `firmware-media` names still map to loopback. Other traffic, such as Google Maps tiles, is unchanged. Connections to literal IP addresses are not intercepted.
- **Power meter in kW.** The Drive tab power meter now spans -100 kW (regen) to +400 kW (drive) in 1 kW steps and writes that kW value to `VAPI_powerLevel`, instead of a -1 to 1 level.
- **Vehicle controls in tabs.** Drive, Wheel buttons and the vehicle-service groups now share one tab bar instead of stacked sections. The power meter (`VAPI_powerLevel`) is a slider on the Drive tab.
- **Car off is not Park.** Car off now also clears `VAPI_driverPresent` and `VAPI_vehicleInAccessoryPlus`, which keep-awake used to force on; Park leaves them on. Charging also sets the charge-port cover and latch (`Engaged`) values. Enum values are read from the firmware libraries, not yet observed on a running UI; check the per-field firmware response.
- **Charging sets the gateway charge state.** The Charging control now also writes `GTW_chargeState` (`Charging`, or `Disconnected` when off), which the lab never set before. Idle values come from parked-car exports; `Charging` itself is not yet observed on a running UI, so check the per-field firmware response.
- **Car off lets the screens sleep.** keep-awake no longer forces `GUI_enableDisplayKeepAlive`, `VAPI_icLCDOn` and `VAPI_icBacklightOn` on every two seconds; they now follow Car off with the other power values, so the firmware sees the car as off instead of being held awake. Car off also shifts to Park and zeroes speed and accelerator, and the Drive feedback line reports the firmware's response for these values as Power.
- **Full reset.** A Full reset button on the Device page, next to QEMU boot check, stops the session and deletes the cached session, engine copy, mount points, library index and saved device settings, like a first import. Firmware, map and QEMU guest files are never touched.
- Fixed Full reset stopping with "A firmware image is still mounted" when a Console shell or leftover process held the mount. Stop and Full reset now unmount the image themselves, lazily if it is busy (safe because it is read-only), and Full reset still never deletes through a mount it could not release. Starting after the FUSE daemon died clears the dead mount and mounts the image again.
- Fixed `pip install -e '.[dev]'` failing on two top-level packages; only `infotainment_lab` is packaged.
- **Documentation.** The README and its links now point to this repository and cover the Console, Vehicle config, Alerts, Service Mode, network isolation, Car off and the power meter. A new [vehicle configuration guide](docs/vehicle-config.md) describes imports, restarts and alerts, and the [compatibility matrix](docs/compatibility.md) is brought up to date.
- **A Console tab.** A terminal on a real pty, with Tab completion, history, Ctrl+C and a blinking caret. On the native Linux/WSL engine it opens a shell inside the running CID's firmware root (read-only, through a user namespace). On the QEMU engine it connects over SSH to the guest through a loopback-only forward (`127.0.0.1:2222`).
- Fixed the QEMU Console opening a plain login on the Debian guest instead of the CID. Connect now enters the firmware image mounted at `/firmware` in the guest (read-only, through a user namespace), as the native engine does; if the image is not mounted it says so and leaves you in the guest shell.
- **One-click SSH key.** Set up SSH key (or the first Connect) creates a lab-owned ed25519 key and authorizes it in the running guest through the guest agent, then confirms it. Guest images built with `scripts/build-virtual-guest.py` include an SSH server with key-only login; older images need a rebuild.
- Works from Windows through WSL2: key setup runs as a backend action and the shell runs inside the distribution.
- **A new configuration import starts from the defaults.** Importing a CSV replaces the previous configuration instead of merging with it: keys the old file set that the new one lacks are removed, and default keys it lacks go back to their default value, so Apply writes those resets too. Values already applied with the same value are not sent again. Editing a value or adding a key by hand still changes only that key.
- **Configuration imports withhold personal data.** Account logins, passwords and PINs, keys, device and network identifiers, and locations in a vehicle dump are never imported, stored or written; the import report lists how many were withheld and the session store refuses them. Live display and power state is listed but never written.
- Fixed a configuration import driving the displays with another car's live readings. Dumps that repeat each name (joined exports) turned telemetry such as `POWER_centerDisplayState` into pending writes, which kept the center display power-cycling. Repeated live values are now listed only, like single ones.
- Fixed vehicle dumps crashing the session. A dump that sets another UI language makes the firmware restart itself, and it sometimes aborts or segfaults while doing so; these are now handled as configuration restarts. Language settings that contradict each other (for example English language with a Norwegian manual language) are dropped after three restarts instead of looping, and are listed as conflicts. A Model 3 configuration (`VAPI_carType` `Model3`) can no longer be imported for an image with only the Model S/X interface: the import is refused with a message instead of crashing the center display. Restart also works again after a session has failed.
- A `ModelS2` (refreshed Model S) `VAPI_carType` is kept by the session's state writer instead of being reset to the default.
- **Service Mode panel (experimental).** The Service card no longer waits for a browser that was never started: the lab now runs the firmware's own `service-ui` backend and its `chromium-odin` window, as the vehicle does. The backend runs in its own unprivileged network namespace, which gives it the vehicle-network address it requires without changing the host network; its page is relayed to `localhost:8000`, and the firmware's `QtCarDvServer` supplies its vehicle values. Rerun Runtime Setup (or reload the AppArmor profile) so SpotifyServer and ChromiumAdapter accept the data-value server. Its token and identity checks are unchanged, and no diagnostic engine or vehicle link is provided, so functions that need them stay unavailable.
- **Service Mode task catalogue (experimental).** The Service panel now has an Odin engine to talk to: a lab stand-in (`runtime/odin-engine.py`) answers the firmware `service-ui` backend's D-Bus calls (`com.tesla.Odin`) and engine websocket. The panel lists the image's own task catalogue (691 tasks on the 2026.8.3 MCU2 image), gateway-config names, maintenance options and an empty service history. Running a task always ends as a routine error that says no vehicle is attached; config values are placeholders and read-only. The firmware `service-ui` itself is unchanged.
- Fixed the native media card loading forever when the firmware's `media-webapp-server` rejected a flag (such as `-secondary_port`) and exited. The lab now reads the server's `-h` output and passes only the flags that firmware defines.
- Fixed the native Service Mode interface opening outside the center screen. The center window was positioned only once at startup; the supervisor now checks every two seconds, pins the main window to the origin and moves any later firmware window (Service Mode, dialogs) back inside the screen. Browser windows are untouched.

## Unreleased — CAN channels and gateway emulation

- **A local CAN service.** The vehicle's own channel names — VEH, CHASSIS and PARTY — over SocketCAN `vcan` interfaces, with a software hub fallback when the kernel module or privileges are missing. Frames are traced per channel and decoded against a frame table.
- **An emulated vehicle gateway.** Per-direction routes with identifier filters, writes from the infotainment side locked by default behind a local HMAC handshake, checksum validation and a rate limit. Accepted climate and lighting requests feed back into vehicle services.
- **A CAN & gateway panel.** Start the service, watch the lock state and per-channel counters, unlock, send a frame through the gateway or straight onto a channel, and read recent frames with decoded signals.
- **Frame definitions and a `.dbc` reader.** The built-in `LAB_*` layouts carry the existing simulator and vehicle-service state; your own database can replace them at runtime.
- The gateway models behaviour only. It contains no vendor protocol, key, certificate or authentication scheme, and reaches no vehicle.
